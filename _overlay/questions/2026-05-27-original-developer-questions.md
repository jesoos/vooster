# 원 개발자 확인 질문 목록

날짜: 2026-05-27
목적: 저장소 내부 증거만으로 확인하기 어려운 생성 과정, 외부 자료, 실행 환경,
의사결정 배경을 원 개발자에게 확인하기 위한 질문 정리

## 질문 방식

가능하면 기억에 의존한 설명보다 실제 자료를 요청하는 편이 좋습니다.

- 원문 프롬프트
- 에이전트 실행 로그
- 사용한 모델과 도구 버전
- 외부 노트나 초안
- 삭제되었거나 squash된 브랜치
- 실패한 실험 기록
- 당시의 로컬 설정 파일 예시

답변을 받을 때는 “무엇을 했는가”보다 “어떤 입력과 검증 루프가 있었는가”에
초점을 맞춥니다. 이 저장소를 따라 만들려면 결과물보다 생성 절차가 더 중요합니다.

## 우선순위 1. 최초 부트스트랩 이전의 자료

이 영역은 저장소만으로 가장 복원하기 어렵습니다.

1. [docs/ideation.md](../../docs/ideation.md) 외에 제품 구상을 위해 사용한
   다른 대화, 노트, 문서가 있었나요?
2. 최초 커밋 전 `GOAL.md`, [AGENTS.md](../../AGENTS.md),
   [docs/](../../docs/), [scripts/](../../scripts/)를 만들게 한 실제 프롬프트
   원문이 남아 있나요?
3. 최초 커밋의 74개 파일은 한 번의 에이전트 실행으로 만들어졌나요, 아니면 여러
   번의 생성 결과를 사람이 합쳐서 정리했나요?
4. 최초 커밋 전에 버려진 구조나 실패한 초안이 있었나요?
5. Cockburn 유스케이스, autonomous build harness, Codex `goal` 설계에 참고한
   외부 문서나 다른 저장소가 있었나요?

## 우선순위 2. 사용한 도구와 실행 환경

재현 가능성에 직접 영향을 주는 질문입니다.

1. 최초 MVP 구현 당시 사용한 코딩 에이전트는 Codex `goal` 하나였나요, Claude
   Code도 함께 사용했나요?
2. 사용한 모델명, 요금제, 컨텍스트 길이, temperature 같은 주요 설정을 기억하나요?
3. `codex goal`은 어떤 명령으로 실행했나요? 실제 입력은 `GOAL.md` 전체였나요,
   아니면 다른 wrapper prompt가 있었나요?
4. 한 번의 goal 실행이 몇 시간 또는 몇 iteration 정도 지속되었나요?
5. 실패하거나 중단된 goal 실행은 어떻게 재개했나요?
6. 로컬 환경은 어떤 OS, Node, pnpm/npm, Docker, Postgres 구성으로 시작했나요?
7. 에이전트가 병렬로 여러 세션에서 동시에 작업했나요, 아니면 순차 실행이었나요?

## 우선순위 3. 사람의 개입 수준

저장소 히스토리만으로는 사람과 에이전트의 경계를 정확히 알기 어렵습니다.

1. 사람은 주로 어떤 순간에 개입했나요?
   - 최초 명세 작성
   - 실패한 테스트 수정 방향 제시
   - 아키텍처 변경 결정
   - UI/UX 판단
   - 커밋 리뷰와 revert
2. `red`, `green`, `refactor` 커밋은 대부분 에이전트가 직접 만들었나요?
3. 사람이 직접 작성한 핵심 파일이나 커밋이 있다면 어느 부분인가요?
4. 에이전트가 잘못 만든 코드를 사람이 크게 다시 쓴 사례가 있나요?
5. main 브랜치에 직접 push하는 위험을 감수한 이유는 무엇인가요?

## 우선순위 4. 하네스 설계 의도

이 저장소의 핵심은 앱 코드보다 하네스입니다.

1. [scripts/diagnose.sh](../../scripts/diagnose.sh),
   [scripts/next-task.sh](../../scripts/next-task.sh),
   [scripts/completion-check.sh](../../scripts/completion-check.sh)는 처음부터 현재
   같은 역할로 설계했나요?
2. [docs/state/](../../docs/state/)를 에이전트 메모리 압축 장치로 설계한
   의도적인 결정이었나요?
3. [scripts/check-bypass.sh](../../scripts/check-bypass.sh)와
   [scripts/verify-tdd.sh](../../scripts/verify-tdd.sh)는 실제로 어떤 문제를
   막기 위해 추가했나요?
4. [goals/](../../goals/)의 `.md`, `.gates.sh`, `.next-task.sh` 3종 세트는
   언제 도입했나요?
5. [docs/goal-design.md](../../docs/goal-design.md)의 universal claim과 gate
   enumeration 원칙은 처음부터 있었나요, 아니면 실패 경험 후 생겼나요?
6. gate cache와 parallel completion check는 성능 문제 때문에 추가한 것인가요?

## 우선순위 5. 명세와 구현의 진화

현재 구조는 최초 구조와 다릅니다. 그 변화의 이유를 확인해야 합니다.

1. 최초에는 root `src/`, `tests/`, `prisma/` 구조였는데, 왜
   [apps/](../../apps/) monorepo로 전환했나요?
2. [packages/contracts/](../../packages/contracts/)는 어떤 문제를 해결하려고
   추가했나요?
3. [apps/app/](../../apps/app/)와 [apps/www/](../../apps/www/)는 처음부터
   계획에 있었나요, 아니면 나중에 필요해졌나요?
4. [docs/09-bootstrap.md](../../docs/09-bootstrap.md)처럼 superseded된 문서는
   왜 삭제하지 않고 남겼나요?
5. 현재 문서와 구현이 불일치하는 부분은 의도적으로 남긴 것인가요, 아니면 아직
   정리되지 않은 부채인가요?

## 우선순위 6. 프롬프트 캐싱과 비용 관리

저장소에는 프롬프트 캐싱을 고려한 흔적이 있지만, 실제 운용 방식은 저장소만으로
부족합니다.

1. 매 iteration마다 반드시 읽게 한 문서와 필요할 때만 읽게 한 문서를 어떻게
   나누었나요?
2. 컨텍스트가 너무 커졌을 때 어떤 문서를 줄이거나 분리했나요?
3. 비용 폭증을 막기 위해 사용한 규칙이나 스크립트가 있었나요?
4. [scripts/cost-monitor.sh](../../scripts/cost-monitor.sh)는 실제로 사용했나요?
5. 긴 [docs/ideation.md](../../docs/ideation.md)는 실제 에이전트 루프에서
   반복적으로 읽혔나요, 아니면 최초 설계 기록으로만 남겼나요?

## 우선순위 7. 실패 사례

성공한 히스토리만 보면 재현에 필요한 제약을 놓치기 쉽습니다.

1. 에이전트가 반복해서 실패한 유형은 무엇이었나요?
2. 테스트를 약하게 만들거나 우회하려는 패턴이 실제로 있었나요?
3. 하네스가 잘못된 다음 작업을 제시한 적이 있었나요?
4. completion check가 green인데 실제 제품은 깨진 사례가 있었나요?
5. 사람의 판단 없이는 해결하기 어려웠던 결정은 무엇이었나요?
6. 지금 다시 시작한다면 처음부터 다르게 설계할 부분은 무엇인가요?

## 우선순위 8. 위임과 다중 에이전트 운용

현재 저장소에는 Codex와 Claude 양쪽 흔적이 있습니다.

1. 어떤 작업을 Codex에 맡기고, 어떤 작업을 Claude Code에 맡겼나요?
2. [docs/claude/delegation.md](../../docs/claude/delegation.md)는 실제 운영 중
   어떤 문제를 해결하려고 도입했나요?
3. UI/UX 작업은 왜 looping agent 대신 Claude Code headless에 위임했나요?
4. [.codex/agents/](../../.codex/agents/)와
   [.claude/agents/](../../.claude/agents/)의 역할 정의는 실제로 얼마나
   자주 사용했나요?
5. 여러 에이전트가 동시에 작업할 때 충돌은 어떻게 관리했나요?

## 우선순위 9. 재현을 위해 직접 요청할 자료

가능하면 아래 자료를 요청합니다.

- 최초 `GOAL.md` 원문
- 최초 부트스트랩 프롬프트 원문
- `codex goal` 실행 명령 예시
- 실패한 초기 실행 로그
- 최초 10개 iteration의 실제 명령/출력 로그
- 하네스 설계 전후 비교 자료
- monorepo 전환 당시의 판단 기록
- Claude Code headless 위임을 시작한 첫 작업 예시
- 직접 사람이 수정한 대표 커밋 목록
- 지금 다시 만들 때 추천하는 최소 템플릿

## 대안 방안

질문 목록만으로 부족하면 다음 방안을 병행합니다.

1. **작은 재현 실험**
   - 5개 유스케이스짜리 새 저장소를 만들고, 이 문서의 절차대로 최소 하네스를
     재현합니다.
   - 어느 단계에서 막히는지 기록하면 원 개발자에게 더 날카로운 질문을 할 수
     있습니다.

2. **히스토리 기반 역공학**
   - 최초 100개 커밋을 시간순으로 읽고, 각 커밋이 어떤 `next-task` 출력에
     대응했을지 추정합니다.
   - 저장소 내부 증거만으로 가능한 한 “실행 로그에 가까운” 타임라인을 만듭니다.

3. **하네스 템플릿 추출**
   - [AGENTS.md](../../AGENTS.md), [scripts/](../../scripts/),
     [goals/0-init.md](../../goals/0-init.md) 계열을 일반화해 새 프로젝트용
     starter template으로 만듭니다.
   - 이 방식은 원 개발자 답변을 기다리지 않고도 실험을 시작할 수 있습니다.

4. **증거 등급 표시**
   - 기존 분석 문서의 주장마다 `확실`, `강한 추정`, `약한 추정`, `원 개발자 확인 필요`
     같은 등급을 붙입니다.
   - 저장소 안의 근거와 외부 확인이 필요한 부분을 분리할 수 있습니다.

현재로서는 1번 질문 목록과 4번 증거 등급 표시를 먼저 하고, 이후 실제로 따라
만들 계획이 생기면 1번 재현 실험과 3번 템플릿 추출을 진행하는 방식이 가장
실용적입니다.
